# W3 原理笔记：Agent 循环到底是谁在转

> 目的：把"手写 ReAct"和"框架原生 Tool Calling"跑在同一批工具、同一个模型下，看清框架到底替我做了什么、又隐藏了什么。
> 代码：`agent/ReActAgent.java`（手写）、`agent/NativeToolAgent.java`（框架），工具在 `tools/`。启动后打开 http://localhost:8083 并排对比。

## 一、两条链路的真实差别

| 环节 | 手写 ReAct | 框架 Tool Calling |
|---|---|---|
| 工具怎么告诉模型 | 工具清单拼进 **system prompt**（`ToolRegistry.describe()`） | 走 API 的 **tools 参数**，框架从 `ToolDefinition` 生成 JSON Schema |
| 模型怎么表达"我要调工具" | 输出**文本**：`Action: xxx` / `Action Input: xxx` | 返回结构化的 **tool_calls**（函数名 + JSON 参数） |
| 谁来解析 | 我自己写正则（`ReActAgent` 里那四个 Pattern） | 框架，无需解析 |
| 谁来执行 | 我 `ToolRegistry.execute()` | 框架内部循环里执行 |
| 结果怎么回填 | 我手动拼 `Observation:` 追加进历史 | 框架自动追加 tool 消息 |
| 循环终止 | 我的 `for (step ≤ maxSteps)` | 框架内部循环 |
| 中间思考可见吗 | **看得到**（Thought 全文） | 看不到自然语言思考，只能靠工具回调埋点 |
| 模型每步耗时 | 测得到（我发起的调用） | **测不到**（调用在框架内部） |

一句话：**框架把"协议解析 + 执行 + 回填"三个环节接走了，代价是中间过程默认不可见。**
和 W2 那个"切分器看着能用、其实参数没生效"是同一类教训：省事的地方，正是你要多看一眼的地方。

## 二、实测（2026-09-19，deepseek-chat，本机 8083）

| 问题 | 手写 ReAct | 框架版 |
|---|---|---|
| 手册查远程办公天数，再按 4.3 周算（**检索 + 计算两步**） | 3 步 / 2287 ms | 2 次工具调用 / 3345 ms |
| 杭州今天天气 | 2 步 / 1434 ms | 1 次调用 / 1342 ms |
| (1200\*0.8)+50 等于多少 | 2 步 / 1062 ms | 1 次调用 / 1159 ms |

> 步数口径：手写版最后那个"给出 Final Answer"也算一步，所以「2 步」≈「1 次工具调用」，两边可比。
> 耗时口径**不一样**（手写版含模型调用，框架版只含工具执行），所以这三个耗时数字只能看个大概，不能当性能对比结论——这条已经写进 `AgentStep.costScope`，前端会标出来。

**两个实现都正确走完了多步推理**：第一步查手册拿到"每周最多两天"，第二步调计算器算 `2*4.3=8.6`，第三步给结论。模型没有跳过工具直接编答案。

## 三、踩坑：框架的 schema 要求参数是 object

`FunctionToolCallback.builder(name, fn).inputType(String.class)` 直接跑，DeepSeek 直接返回：

```
400 Invalid schema for function 'calculator':
schema must be a JSON Schema of 'type: "object"', got 'type: "string"'
```

原因：OpenAI 兼容的 tools 协议规定，函数的参数顶层必须是 object（因为要按名字取参数）。
`inputType(String.class)` 生成的是 `{"type":"string"}`，所以不合规。**修法**：包一层记录 `ToolInput(String input)`，schema 变成
`{"type":"object","properties":{"input":{"type":"string"}}}`，模型按 `{"input":"2*4.3"}` 调用。

手写 ReAct 完全没有这个约束——`Action Input` 本来就是一行自由文本。这条正好说明框架的作用范围：
**它标准化的是"模型与工具之间那一层协议"**，而你为此付出的代价，是工具的参数形状得按它的规则来。

## 四、工具本身怎么设计（比框架选型更重要）

- `description()` **直接决定模型会不会用、用得对不对**。把"输入是城市名，例如 杭州"写清楚，模型就老老实实传 `杭州`，
  而不是把整句问题塞进去（实测三条问题里，工具输入全部干净）。
- **工具要能失败得体面**：`ToolRegistry` 里查不到工具名、工具抛异常，都不往外抛，而是把错误当 `Observation` 回给模型，
  让它有机会自己改正。Agent 的鲁棒性一半在这。
- **安全边界**：`CalculatorTool` 宁可用 30 行递归下降解析器，也不上脚本引擎 eval——输入是模型给的字符串，
  交给 eval 等于把任意代码执行权交出去（提示词注入 → 参数注入 → 代码执行）。
- **工具可以换实现、不换接口**：`WeatherTool` 现在是硬编码的示例数据，换成真实 HTTP API 时 Agent 侧一行都不用改。
  `HandbookSearchTool` 最早是关键词版检索（没有 embedding）；W4 换成调 rag-demo 的检索接口，**Agent 侧一行都没改**——
  这就是"工具是接口不是实现"的实证，见 §六。

## 五、W4：把 RAG 接成工具（作品 1 → 作品 2）

两个服务分开跑，各自职责单一：

| | 端口 | 职责 | 接口 |
|---|---|---|---|
| rag-demo（作品 1） | 8082 | 切分 / 向量化 / 检索，**只回片段不生成** | `POST /api/knowledge/search` → `[{text, score}]` |
| agent-demo（作品 2） | 8083 | 编排：判断要不要查、查什么词、怎么用结果 | `POST /api/agent/react` \| `/native` \| `/compare` |

为什么拆开而不是把 RAG 代码搬进来：检索是**能力**，生成是**策略**。
rag-demo 只管"给定问题，最相关的 N 个片段是什么"，至于要不要拿去组织成答案、要不要再补一次工具调用，
是 Agent 的决定。拆开以后两边可以独立换实现（换向量库、换编排框架），接口不变。
代码上体现为 `${AGENT_KNOWLEDGE_BASE_URL:http://localhost:8081}` —— 环境变量覆盖，不写死在代码里。

### 踩坑：两条路径的 prompt 不是同一套（差点当成"模型随机性"）

同一个问题「公司裁员会赔几个月工资？」，两版答案差很多：

- 手写 ReAct：`资料中没有相关信息`，很干净。
- 框架原生：也说知识库没有，但**接着补了一段《劳动合同法》的 N+1 补偿标准**。

第一反应是"模型有随机性"，但连着跑了几次差异都在同一个方向，才回去查代码——**框架版的 `chatClient.prompt()` 根本没有 system prompt**。

原因：最初我只把手写版的约束写进了 `ReActAgent.systemPrompt()`，框架版连 `.system()` 都没调，
它手上的规矩只有工具的 description。两边跑的压根不是同一套指令，这个对比从一开始就不成立。

**修法**：抽出 `AgentPrompts.behaviorRules()`，两条路径共用；prompt 里分开"协议规则"（Thought/Action 怎么写，ReAct 特有）
和"行为约束"（什么能说什么不能说，共用）。

教训比 bug 本身值钱：**做对照实验，先把"除了变量以外的东西都一样"验证一遍。**
两版差异大的时候，第一嫌疑是代码写错了，不是模型不稳定。

### 第 7 条的由来：拒绝回答 ≠ 对用户最有价值

修完之后 Q4 两边都拒绝编造了，但会走到另一个极端——只回一句"资料中没有相关信息"，用户什么也没拿到。
所以加了第 7 条：**允许补充公司资料之外的常识，但必须显式标注"这不是公司规定"**。

实测（2026-09-20，3 个问题，两版并跑）：

| 问题 | 手写 ReAct | 框架原生 |
|---|---|---|
| Q1 远程办公每周几天 + 按 4.3 周折月（检索 + 计算） | 3 步 / 3633 ms | 2 次工具调用 / 3459 ms |
| Q4 裁员赔几个月（**知识库里没有**） | 1 次检索 / 2625 ms，拒绝 + 标注法律常识 | 2 次检索 / 3528 ms，拒绝 + 标注法律常识 |
| Q5 试用期能否远程办公（片段里有一句关键的） | 1 次检索 / 1737 ms，答"不能"并引原文 | 2 次检索 / 3850 ms，答"不能"并引第 8 条 |

**这里推翻了我自己 W3 时的一个印象。** §二那张表里框架版看着更快，接上知识库之后反过来了：
Q5 是 3850ms vs 1737ms，差了一倍多。原因不是框架慢，是**框架版自己多追加了一轮检索**
（`试用期 远程办公 申请` 没查到满意结果，又换 `远程办公 每周几天 申请条件` 试了一次），
而手写版一查不爽就直接收尾了。

所以准确的说法是：**工具调用轮数才是耗时的主要变量**，不是"手写 vs 框架"。
W3 那三个问题的耗时结论只在"工具都是一把过"的场景下成立，样本太小，当时不该写那么满。

### 顺带一个产品判断

框架版多搜一轮这件事，性能上是浪费，效果上却常常更好（Q5 它引到了第 8 条原文，引用更准）。
"该不该多查一轮"取决于你这个场景更怕浪费还是更怕漏——这类取舍没法在代码里一刀切，
要么给 maxSteps 上限兜底，要么把轮数做成可配的。

## 七、W4：会话记忆（短期上下文 + 长期画像）

### 两种记忆的分工，别混在一起

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 存什么 | 这个会话里聊过什么 | 这个人是谁（部门/职位/入职时间/偏好） |
| 作用域 | sessionId | userId |
| 会过期吗 | 会，按轮数裁剪 | 不该过期，跨会话保留 |
| 存哪 | `ConversationMemory` | `UserProfileStore` |
| 怎么进 prompt | 消息列表 / 拼进用户消息 | system prompt |

混在一起会怎样：用户说"我是技术部的"，你把它当历史按轮数丢掉，下次开新会话它就不认识这个人了——
可这句话明明永远不会过期。**判据是"这条信息会不会过期"，不是"它是谁说的"。**

### 架构上的一个决定：Agent 保持无状态

`run(question, ctx)` 只**读**上下文，不写。写入放在 Controller 里，流程是：

```
读记忆 → 组装 RunContext → 跑 Agent（纯函数） → 写记忆
```

好处：Agent 可以拿同样输入重放（好测）；记忆策略要换（Redis、加摘要压缩、按 token 动态裁剪）只改一处。

### 工具怎么知道"当前是谁"——ToolContext

`memory_save` 必须知道给谁记，但 **userId 不能让模型传**：它不知道，你让它传它只会编一个
（用户说"我是技术部的"，它完全可能填 `userId=技术部`）。

所以走运行时上下文：框架版用 `BiFunction<ToolInput, ToolContext, String>` + `.toolContext(Map)`，
手写版走 `ToolRegistry.execute(name, input, ctx)`。`Tool` 接口用 default 方法加了带上下文的重载，
**不需要上下文的工具（计算器、时间、检索）一行都没改**——接口演化时默认方法的用处就在这。

（用 `Map` 而不是直接暴露 Spring AI 的 `ToolContext`：手写那条路径不该被迫依赖框架的类。
转换在 `NativeToolAgent` 里做，一行。）

### 实测踩到的三个坑

**坑 1：记忆的键只用 sessionId，两个用户串了。**

最初 `ConversationMemory` 是 `Map<sessionId, List<ChatTurn>>`。测试时我让 u9 和 u10 恰好都用了
sessionId=`Q`，结果 u10 问"我在哪个部门"，答出了 **u9 的部门**。画像那边是按 userId 隔离的、没事，历史这边穿了。

sessionId 是前端给的，不受你控制——可以手输、可以从 URL 拿、可以复用旧值。
把它当身份，等于把 A 的对话摊给 B 看。改成 `Map<SessionKey(userId, sessionId), ...>` 后复测：
uE 复用 uD 的 sessionId，正确回答"我这边还没有你的信息"。

**修完要说的下一句是：这不是靠这个键能防住的**——真正要防的是"用户能随便声称自己是别人"，
那得靠鉴权。键里带 userId 只是纵深防御的一层，别把它说成安全方案。

**坑 2：画像为空时"不注入"，模型就编了个假理由。**

没有画像时我原本直接不拼那一段 prompt。结果用户问"我在哪个部门"，模型答：
> 我只有写入长期记忆的能力…但没有读取个人信息的工具，所以无法告诉你

**它没有这个限制，是它自己编的。** 根因不是模型爱撒谎，是 prompt 里留了空白：
"查不到"和"没这个能力"在模型看来是同一件事，它就挑了听起来更合理的那个解释。
改成显式注入「（暂无）你还不知道这个用户是谁，需要就直接问，**不要解释成『你没有读取权限』**」后复测，回答变成：

> 我这边还没有你的信息，不知道你在哪个部门。可以告诉我吗？

**教训：缺信息的时候，你得明确告诉模型"就是没有"，而不是什么都不说。**

**坑 3：模型把多组信息挤进一行，两条事实并成一个键。**

用户说"我叫王五，在市场部，记一下"，模型调了一次 `memory_save`，参数是
`姓名=王五, 部门=市场部`。我的解析按第一个 `=` 切，结果画像里出现一条
`姓名 = 王五, 部门=市场部`——部门这条事实等于丢了（下次问部门它答不出来）。

修法不是改 prompt 了事：description 里写"一次一条"是**概率性**的，模型下次照样可能挤一行。
真正确定的是解析层——按"逗号后面跟着下一个 key="的规则切分，同时 description 改成"可以用逗号传多组"。
复测一条 `姓名=赵六,部门=研发部,入职时间=2024年5月` 正确拆成 3 个键。

（切分规则是启发式，不是完备解析：只在逗号后面确实像新 key 时才切，避免把
`地址=杭州市,西湖区` 切开。真要严谨得走结构化 JSON 参数，但手写 ReAct 那条路径只有纯文本。）

### 上限是不是真的生效（实测，不是"写了就算"）

- 单会话连问 7 轮：历史稳定在 **12 条**（6 轮 × 2），第 1 轮被丢掉，窗口是第 2–7 轮 → 裁剪真的在丢。
- 正确性上顺带确认：**工具 Observation 不写进历史**。检索片段动辄几百字，写进去几轮就把上下文顶满，
  而它对下一轮的价值远不如一个结论。
- 画像上限（20 条/用户）和会话数上限（200，LRU）**只写了代码，没实测**——要压得造成 200 个会话，
  属于可以但没必要，如实标出来。

### 局限（面试主动说，别等对方问）

- **全在堆内存**：进程重启即清空、多实例部署不共享。W4 测试过程中我重启了一次服务，
  再问"我在哪个部门"直接变成"我这边还没有你的信息"——这个局限是**实测撞到的，不是推测**。
  上生产换 Redis（会话 TTL）+ 数据库（画像），`append/history` 这层接口不用动。
- 历史是**截断**不是**摘要**：聊到 20 轮以后早期内容直接消失。更好的做法是超过阈值后用小模型压缩成摘要，
  但那是另一个工程量级，现在不做，也不吹。
- 画像**没有删除接口**（只有整体 clear）。真实系统里"删除用户数据"要按合规流程走，不是随手加个 DELETE。

## 六、还没验证的（别当结论讲）

- 框架内部那个循环的**步数上限**是多少、超限怎么表现——没测过，需要构造一个"模型反复调工具"的场景来压。
- MCP：W3 计划里还有"跑通一个 MCP Server/Client"，**尚未开始**。
- 画像上限（20 条）、会话数上限（200 LRU）没实测，只有代码。
- §五那三条实测样本只有 3 个问题，**不足以支撑性能结论**，只能当现象记录。
- 记忆只在这两个进程内验证过，**没测过并发**（两个请求同时写同一会话会怎样）——
  代码里用 `synchronized` 挡了容器层的并发，但没有压测证据，别当成"并发安全已验证"。
